# AirSprint Android 6.1.12 and customs workflow audit

## Evidence

Google Play installation on 1 October 2026: AirSprint 6.1.12, code 135,
Flutter/Dart 3.12.2. The disposable emulator was updated without changing the
normal emulator snapshot. Base APK SHA-256:

`f9f689cf22a6c74558800d468765bdbb1c293713f1fe87057ab0ca774d2284e5`

The decompiled app contains 111 repository requests and 105 unique routes.
The removed duplicate lock-flight call does not remove the route. Source
locations and new instruction addresses are in `scripts/android_contracts.json`.
Raw APKs, analysis, private service responses and passport scans remain ignored.

## Findings and changes

1. **Customs were attributed to the wrong leg.** Live link responses showed
   submitted outbound declarations and non-submitted Canadian-return
   declarations for the same travellers. Selection now targets the active
   Canadian arrival and rejects ambiguous or cancelled legs.
2. **The old signature guidance was wrong.** The app's certification checkbox
   is local. Its submit repository sends the form directly, without a separate
   certification field or signature endpoint. `customs status` reports the
   server's actual `customsDeclarationAlreadySubmitted` per traveller and leg.
3. **Preparation is now separate from submission.** `prepare`/`create` only
   write local drafts. Missing answers are retained as blockers. `review` is
   offline; edits use typed options and invalidate all prior certifications.
   Each traveller must be certified separately. Final `submit --confirm`
   checks for changed itinerary/passports/addresses and previously submitted
   passengers before one POST per form. Family grouping requires explicit
   same-address confirmation, max four, with individual certifications.
4. **Duplicate prevention survives failures.** Draft state and a private
   submission journal are written before a POST. Unknown/partial outcomes
   remain blocked, even from a different draft on the same machine. Requests
   are never retried. Post-submission date editing is retired.
5. **Passport file format was not the failure.** Android explicitly accepts
   PDF/JPG/PNG. Private originals and API records showed that same-named saved
   and trip profiles can have different IDs, scans and passport selections.
   The trip audit identifies orphaned selections and missing scans; passport
   listing now accepts the actual trip passenger ID, including unsaved guests.
   One authority discrepancy was found by visually comparing a scan; no
   passport numbers or personal details are stored in this report.
6. **Passenger updates copied invalid address values.** A recorded rejection
   showed `destinationAddress.street2: null` was refused. Updates now serialize
   only the Android address keys with null/empty optional values omitted and
   preserve `selectedPassportId` through the request's `passport: {id}` field.
7. **Other 6.1.12 parity updates:** active-account sharing eligibility;
   `filter.name` for fallback airport resolution; failure envelopes checked
   even when transport HTTP status is 200.
8. **Drafts always identify the traveller by full name.** Generated and
   explicit filenames use `BOOKING-firstname-lastname.json`, with every full
   name included for grouped drafts. Accents are normalized. First-name-only
   passenger selections and filename aliases are rejected. Repeating a new
   preparation cannot overwrite an existing draft.

## Validation and limits

180 offline tests pass locally. Ruff and `git diff --check` pass. Live
validation also completed three separate Canadian-return declarations after
individual certification and the owner's explicit final submission approval.
Each form was sent once and returned a declaration ID. All three local drafts
and journal entries record the accepted submissions. Private receipts and
personal data remain outside the repository.

Offline regression tests cover route inventory, request bodies, family vs
individual forms, incomplete drafts, individual certifications, invalidation
on edits, stale/changed trip fields, missing and already-submitted flags,
partial failures, timeout replay, cross-draft replay, private files, and
non-retried API errors. Tests mock service calls; no test creates a real booking,
passport or declaration. The initial investigation used authorized reads and
existing operation artifacts. After the owner's explicit instruction,
one authority-only passport PATCH corrected the discrepancy. The response
returned the corrected authority, and the refreshed draft confirmed it on the
trip profile. Declaration answers were reviewed and certified locally before
submission. Each submission checked the current leg and submitted flags before
its single POST; no automatic retry or post-submission read-back was performed.

Client-side locking prevents simultaneous submissions on this machine. The
API has no verified idempotency-key contract; submissions must not be run
concurrently from different machines. The journal is intentionally conservative
and requires manual resolution of uncertain outcomes. A saved scan does not
by itself prove its contents match the data; individual review remains required.
