# AirSprint CLI audit — 2026-09-16

## Result and scope

The invalid booked-leg pre-read is fixed. The CLI was then checked against
AirSprint Android **6.1.10, version code 133**, installed directly from Google
Play in an isolated, disposable emulator session. No booking, passenger,
passport, customs declaration, or account was changed on the AirSprint service.

The source audit covers every Android repository API call and every statically
resolved CLI API call, including supporting reads and upload destinations.
Request models, response identifiers, authentication, booking guards, document
workflows and command help were also reviewed. This is source and offline
behavioral validation; it does not certify every production endpoint or access
permission by making real mutations.

## Findings corrected

| Finding | Before | Corrected behavior |
|---|---|---|
| Wrong booked-leg read route | Three flows used `GET /leg/{id}`, absent from the Android GET inventory. A 401 prevented the subsequent write. | `leg update-required-info`, `leg update-passengers` and `customs create --leg-id` use `GET /my-leg/{id}`. The PATCH destinations are unchanged. |
| Incomplete passenger response | A response without a recognized passenger-list field became `[]`, potentially replacing the real passenger list. | Missing/malformed lists abort before a write. Unresolved saved-passenger IDs are also rejected. |
| Token identity mismatch | A valid cached token won even when a different `--username` was supplied. | Cached tokens are reused only for the requested email; malformed/expired cache records are rejected. |
| Incomplete 2FA workflow | Login hid the challenge's user ID; 2FA sign-in printed the token response without saving the session. | Login explains the next step and exposes the challenge identifier. Successful 2FA saves the session without printing the token; failed 2FA does not replace it. |
| Unverifiable passport scan | An international booking could pass when the passenger read contained only passport IDs. | Missing full passport data or an absent selected passport fails closed; no booking is sent. |
| Passport ownership on reorder | `make-primary` could prepend an arbitrary passport ID. | The chosen passport must already belong to that passenger. |
| New Android arrival transport | The CLI exposed only departure transport on shared/empty-flight bookings. | The three arrival transport options added in Android 6.1.10 are supported. |
| Ignored display timezone | Several commands accepted `--timezone` without using it for output. | Commands that accept the option apply and validate it; presentation state resets between CLI invocations. |

The initial incident report is consistent with the old code and Android's
owner route. The reported historical HTTP 200 and saved destination addresses
were not independently replayed or re-read during this audit.

## Android comparison

The fresh inventory contains **112 request call sites, 105 unique method/route
contracts**: 21 GET, 65 POST, 11 PATCH and 8 DELETE. All 104 contracts from
6.1.4 remain present. The new route is `GET /app-update`, used for native-app
upgrade prompts with `version` and optional `buildNumber`, without an owner
token. It is deliberately outside this Python CLI's user-facing operations.

Of the 105 contracts, **102 are exposed**. The three deliberate omissions are
`/app-update`, `/file-public/create` and `/leg/recent/save`; see
`ANDROID_CONTRACT.md`. The separately verified customs-date PATCH remains an
explicit extension, not an invented Android contract.

The comparison of 184 common request-related functions found 172 unchanged
after normalizing assembly addresses. The remaining 12 were reviewed: method
wrapper ordering and runtime class-number changes, reconstruction of service
settings from responses, and the new arrival transport fields. Address
normalization is a review aid, not proof of semantic equivalence on its own.

The reviewed workflow families were:

| Family | Checks |
|---|---|
| Trips, booking, required information | Owner reads vs write routes; complete passenger lists; saved IDs vs leg-passenger IDs; options envelopes; passport/address guards; single writes and cooldowns. |
| Shared/empty flights | Passenger envelope, conditional pets/baggage, catering, departure and newly added arrival transport; no invented passport/customs/note fields. |
| Passenger, passport and pet profiles | Create/update/delete routes and payload envelopes; passport ordering; document-init, presigned multipart POST and attach steps. |
| Customs | Link creation, declaration field spelling and conditionality, leg-passenger IDs, date conversion, bounded passenger resolution. |
| Quotes and hours exchange | GET query parameters vs POST bodies, passenger counts, conditional cost fields, listing envelopes. |
| Account, user and authentication | Invite roles and account IDs, patch envelopes, notification registration/settings, login and 2FA token handling. |
| Network, content and files | Method/route mapping, identifiers, batch bodies, bodyless collections and bounded file resolution. |

## Validation

The regression suite includes an independent route check against the extracted
Android snapshot. It checks actual call expressions, local path variables,
conditional destinations and document-upload arguments. An unknown route or an
unresolved dynamic route fails the test. Hidden maintainer raw commands and the
documented customs-date extension are explicitly separated.

Validation commands:

```sh
cd scripts
python3 -m unittest test_airsprint_cli
cd ..
ruff check scripts/airsprint_cli.py scripts/test_airsprint_cli.py
python3 -m py_compile scripts/airsprint_cli.py scripts/test_airsprint_cli.py
git diff --check
```

Final verification: **156 tests passed** with live socket connections blocked;
**119 public leaf commands** passed `--help` with authentication disabled.
Ruff, Python compilation and `git diff --check` passed. Test and help-check
artifacts are saved locally under `tmp/audit-2026-09-16/`.

## Limits and release considerations

- No live AirSprint mutation was used as a test. Server permission or persistence
  behavior still requires a legitimate, user-authorized operation; never send
  a booking or document upload merely to prove an audit claim.
- Existing shared/empty-flight requests contain no passport field. The CLI
  cannot infer border-crossing requirements there without an additional flight
  read; its stricter passport/address guard currently applies to `booking create`.
- Required-info and add/remove-passenger updates depend on one complete owner
  response. They abort on malformed or unresolved passenger data; they do not
  retry another endpoint or automatically read back a successful write.
- Ambiguous live write failures still require reconciliation, not automatic
  retries. Multi-step document creation already reports partial completion.
- Release publication is a separate step after reviewing these changes. The
  local starting commit and `origin/main` were both `c80b7a4` when fetched.
